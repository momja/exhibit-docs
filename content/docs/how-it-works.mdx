---
title: How Exhibit works
description: "Two origins, one write path, and the render sandbox"
---

Exhibit keeps one simple rule: every change flows through the server's HTTP API, and every artifact runs isolated from the gallery app.

## One write path

Whether you build with the agent or paste HTML at `/new`, snapshot a URL, edit source, restore a version, or drive Exhibit from the Pi sidecar, the change goes through the same HTTP API. The gallery UI is a client of that API, not a separate path — so versions, search indexes, and shared state stay consistent no matter which surface made the edit.

## Two origins, one sandbox

The app runs on `APP_ORIGIN` and renders artifacts on `RENDER_ORIGIN`. Each artifact loads in an opaque-origin sandboxed iframe with a per-artifact Content Security Policy built from its approved network allowlist, plus HMAC render tokens scoped to one artifact and expiring after ten minutes, so render URLs can't be forged or replayed. Even a malicious page can't reach gallery credentials or other artifacts' state — unapproved network calls simply fail.

## Storage: metadata plus blobs

SQLite holds metadata (titles, tags, shares, versions, state pointers) with FTS5 powering `/search`, while artifact bodies and snapshots live as blobs on the filesystem or S3. Rows are owner-scoped: requesting an artifact you can't see returns 404, never 403, so private IDs aren't enumerable.

## Observe, don't predict

Exhibit doesn't guess what an artifact will do — it watches what it does. A storage shim preamble runs before artifact scripts to capture `localStorage` writes and sync them automatically through the state endpoint (`PUT /api/artifacts/:id/state`), while `sessionStorage` stays ephemeral in the tab. A CSP reporter records blocked network attempts, which the UI surfaces as allowlist approval prompts.

## Server-rendered UI

Gallery pages are rendered with Go `html/template` and updated with htmx partial swaps — listing pages show 24 cards per page with no full reload. Stimulus controllers own small reusable behaviors (dialogs, menus, paging), styled with Phosphor icons. Page scripts stay dependency-free ES modules, so the UI remains fast and view-source friendly.
